Operator playbook — retrain to hot-swap

Six steps. Most happen here. The two that don't are linked out.

  1. 1
    Check data volume in this dashboard

    Look at the dataset stats appearing in the retrain log when you click "Start retrain".
    Need at least 50 confirmed-fall rows. If short, run
    python -m retrain.seed_test_data --synthetic 200 from a terminal first.

  2. 2
    Retrain + register in this dashboard

    Use the "Retrain" panel below. Tick --register to add the run to the Model Registry.
    The new version appears under "Registered versions" when training finishes.

  3. 3
    Compare metrics & pick a winner in MLflow UI

    Open http://localhost:5000
    → Experiments tab. Compare recall / AUC / F1 against the current Production version. Recall must be ≥ current production before promoting.

  4. 4
    Promote to Production in this dashboard

    Click "Set Production" on the chosen version in the registered-versions table below.
    This moves the alias only — no server change yet.

  5. 5
    Hot-swap the live inference server in this dashboard

    Click "Swap to Production alias" in the hot-swap panel.
    The inference server downloads the new .pkl from MinIO and replaces the
    in-memory model. No restart, no downtime.

  6. 6
    Validate in production in Grafana

    Open http://localhost:3000 → model_performance dashboard. Watch for at least one full day after promotion.
    Roll back immediately if anything looks wrong (use the rollback button below).

How to avoid model drift — checklist

        

          
Model drift means the live model's predictions get worse over time even though the
          code didn't change. There are two flavours, both relevant here:

          
    
            
  • Data drift — the input distribution shifts. New patient demographics,
              different sensor firmware, different wearing position. The model still does what it learned, but
              what it learned no longer matches the world.
    • 
            
  • Concept drift — the relationship between input and label changes.
              For falls this is rare (a fall is still a fall), but it matters if the labelling protocol changes.
    • 
          


          
Signals to watch (Grafana — model_performance dashboard)

          
    
            
  • Median confidence drifts away from its baseline (most often: clusters near 0.5)
    • 
            
  • Fall rate per hour shifts noticeably from the historical baseline
    • 
            
  • Low-confidence ratio rises above ~20%
    • 
            
  • p95 latency stays stable but error rate is increasing
    • 
          


          
When NOT to retrain

          
    
            
  • Fewer than 50 confirmed-fall rows in Postgres (positives). Run
              python -m retrain.retrain --dry-run first to check.
    • 
            
  • You only have synthetic data (seed_test_data --synthetic) — you can validate
              the pipeline this way but never deploy a synthetic-only model to real patients.
    • 
            
  • No operational signal & the data hasn't changed meaningfully — retraining adds risk
              for no benefit.
    • 
          


          
When to retrain

          
    
            
  • An operational signal in Grafana and at least 50 new positives accumulated since the
              last retrain
    • 
            
  • Hardware change (new wearable firmware, new sensor placement) — coordinate retrain with
              the hardware rollout
    • 
            
  • Periodic refresh after a long deployment with no major signals — ~quarterly is usually
              enough
    • 
          


          
Validation rules before promoting to Production

          
    
            
  • Recall must be ≥ the current production model. Missing a fall is far worse
              than a false alarm.
    • 
            
  • AUC ≥ 0.85, F1 ≥ 0.75 — sanity check that the model isn't gaming recall by flagging
              everything.
    • 
            
  • Test set has at least 10 positives and 10 negatives — below this, metrics are noise.
    • 
            
  • Watch Grafana for at least one full day after promotion. Roll back
              immediately if anything looks wrong — do not wait for it to recover.
    • 
          


          
Rollback cheat sheet

          
    
            
  • Move the Production alias back to the previous version (Promote button on a
              registered version)
    • 
            
  • Or use the file-based fallback (Swap to file-based v0 button above) to revert to
              the image-baked model
    • 
          


          
What this UI does NOT cover

          
    
            
  • Adding a new sensor or feature (e.g. barometer) — that's a coordinated rollout, not a
              hot-swap. See handover_docs/ADMIN_runbook_retrain_and_hotswap.md § Decision summary.
    • 
            
  • Hot-swap persistence across pod restarts — not yet implemented. Each pod restart reverts
              to MODEL_VERSION in .env. Re-call hot-swap after every restart until
              this is fixed.
    • 
            
  • Automatic drift-driven retraining — deferred. Currently fully manual.
