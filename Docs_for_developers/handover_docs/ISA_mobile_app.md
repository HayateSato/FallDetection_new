# Mobile App Integration Handover (Isa)

**Audience:** Isa — building the real mobile app that replaces our local-dev `mock_app`.
**Repo / branch:** `_6G_Integration_v2_mqtt/` on branch `6G-integration_with_MQTT`.
**Scope:** What the mobile app must do, what payloads it sends and receives, and the exact contract with our two backend services (inference server + fall_dashboard). For overall architecture see `Tech_integrator.md`. For dashboard API details see `REFACTOR_DOCUS/isa_integration_guide.md`.

---

## 1. The Mobile App's Job in One Paragraph

Your mobile app is the only piece of code that talks to the SmarKo wearable. For each ACC window the wearable produces, the app must (1) POST it to our inference server, (2) if the response says a fall happened, open a "Did you fall?" popup for ~10 seconds, (3) publish an MQTT alert summarising the result of that popup. The inference server has no MQTT client and the fall_dashboard has no HTTP client to the wearable — the mobile app is the only thing that bridges those two protocols. Everything in the rest of this document follows from that.

The local-dev stand-in for your mobile app is `local_dev/mock_app/`. It reads ACC windows from our cloud InfluxDB instead of from BLE, but the rest of the flow (POST `/predict`, simulate the popup, PUBLISH MQTT) is identical. Reading that code is the fastest way to understand what your real app needs to do.

## 2. End-to-End Flow

```
[SmarKo wearable]                                     (BLE)
    │
    ▼
[Mobile App]  ───── HTTP POST /predict ─────▶  [inference_server :8001]
    │ ◀──────── HTTP response (PredictResponse JSON) ──────────
    │
    │  if fall_detected == False  →  log + done. No MQTT, no popup.
    │  if fall_detected == True   →  open patient confirmation popup (~10s)
    │
    │  build alert payload — must include observation_id from the response
    │
    │  MQTT PUBLISH  fall/alert/<patient_id>
    ▼
[MQTT broker :1883 / :9001 ws]
    │  routes to subscribers of fall/alert/#
    ▼
[fall_dashboard :8002]
    │  writes fall_history row to Postgres
    │  fans out via SSE to dashboard browsers
    ▼
[Patient Dashboard browser]  → alert banner appears
```

Two protocols are involved:
- **HTTP**: mobile app → `inference_server` for the prediction.
- **MQTT**: mobile app → broker → `fall_dashboard` for the confirmed-fall alert.

There is no second HTTP call. The mobile app does **not** send anything else to our backend after the MQTT publish.

## 3. The `/predict` Contract

### Request

`POST http://<inference-host>:8001/predict`

Header: `X-API-Key: <key>` (the API key value will be provided once `helm install` is done — not committed to the repo).

Body:

```json
{
  "patient_id":          "test_patient-002",
  "device_id":           "6c:1d:eb:04:a9:e6",
  "timestamp":           "2026-04-27T10:00:00+00:00",
  "acc_x":               [ 8421, 8430, "..." ],
  "acc_y":               [ -120, -118, "..." ],
  "acc_z":               [ 16380, 16382, "..." ],
  "timestamps_ms":       [ 1714212000000, 1714212000020, "..." ],
  "pressure":            [ ],
  "pressure_timestamps_ms": [ ]
}
```

Field rules:

| Field | Type | Notes |
|-------|------|-------|
| `patient_id` | string | The same identifier used elsewhere — must match the FHIR Patient `id` you use on the FOCUS side. |
| `device_id` | string | The wearable MAC address. |
| `timestamp` | ISO8601 string | The time of the **first sample** in the window. |
| `acc_x` / `acc_y` / `acc_z` | array of int | **Raw LSB integers from the Bosch sensor — not g.** 450 samples = 9 s at 50 Hz. The inference server divides by 16384 internally. |
| `timestamps_ms` | array of int | One per ACC sample. Required. |
| `pressure` | array (optional) | Barometer samples. Model v0 ignores it. Pass an empty list. |
| `pressure_timestamps_ms` | array (optional) | Empty list is fine. |

### Response

```json
{
  "observation_id":  "3f7a1b2c-...",
  "patient_id":      "test_patient-002",
  "device_id":       "6c:1d:eb:04:a9:e6",
  "timestamp":       "2026-04-27T10:00:00+00:00",
  "inference": {
    "fall_detected":  true,
    "confidence":     0.8234,
    "threshold":      0.5,
    "result":         "High confidence fall",
    "model_version":  "v0",
    "window_size":    450
  },
  "fhir_observation": { "resourceType": "Observation", "...": "..." },
  "fhir_pushed": false
}
```

What the mobile app must do with each field:

- `observation_id` — **save this.** It is a UUID generated by the server. You will need it again in the MQTT payload (section 5). If you drop it the retraining JOIN breaks silently.
- `inference.fall_detected` — drives the rest of the flow. `false` → done. `true` → show the popup.
- `inference.confidence` — show in the popup if useful, otherwise just include it in the MQTT payload.
- `fhir_observation` — full FHIR R4 Observation resource. Optionally push it to FOCUS's FHIR server yourself, or include it in the MQTT payload as we currently do (we may drop this field once FHIR push is centralised).
- `fhir_pushed` — `true` only when the inference server itself pushed to a configured FHIR endpoint. Usually `false` in our deployment.

The reference reader is `local_dev/mock_app/poller.py:146` — it reads exactly these fields and nothing else.

## 4. The Patient Confirmation Popup

After a fall is detected, your app shows a popup along the lines of:

> "Did you fall? Tap YES if you fell. Tap NO if you didn't."

The popup must close itself if the patient does not respond within a configurable timeout (default 10 seconds — `MOCK_PATIENT_RESPONSE_TIMEOUT` in our `.env`). After it closes, you decide one of three values for `patient_confirmed`:

| Patient action | `patient_confirmed` | `needs_help` |
|----------------|---------------------|--------------|
| Tapped YES | `"yes"` | `true` |
| Tapped NO | `"no"` | `false` |
| No response within timeout | `"not_answered"` | `true` (assumed — patient may be incapacitated) |

The mock_app always produces `"not_answered"` because it has no UI; your real app will produce all three values.

**Open question:** which UI shows this popup? The SmarKo app may already have one, or you may need to add it. Confirm with the SmarKo team and document the outcome here.

## 5. The MQTT Alert

After the popup closes (regardless of how it closed), the mobile app publishes one MQTT message.

| Setting | Value (local dev) | Value (production) |
|---------|-------------------|---------------------|
| Broker host | `localhost` | Kubernetes service — to be confirmed by FOCUS DevOps |
| TCP port | `1883` | `1883` |
| WebSocket port | `9001` | `9001` |
| Auth | none | username/password — to be set before prod |
| Topic | `fall/alert/<patient_id>` | `fall/alert/<patient_id>` |

### Why WebSocket port 9001 matters for React Native

React Native cannot use raw TCP sockets, so it cannot talk to MQTT on 1883. The broker (`eclipse-mosquitto`) is configured with `listener 9001 protocol websockets` — use this port. `mqtt.js` (npm `mqtt` package) works in React Native with no native modules:

```js
import mqtt from 'mqtt';
const client = mqtt.connect('ws://<broker-host>:9001');
```

### Payload

`fall_dashboard` parses the payload with code at `fall_dashboard/mqtt_listener.py:133`. It expects exactly these fields:

```json
{
  "observation_id":    "3f7a1b2c-...",
  "patient_id":        "test_patient-002",
  "device_id":         "6c:1d:eb:04:a9:e6",
  "timestamp":         "2026-04-27T10:00:00+00:00",
  "fall_detected":     true,
  "confidence":        0.8234,
  "model_version":     "v0",
  "alert_time":        "2026-04-27T10:00:10+00:00",
  "patient_confirmed": "not_answered",
  "needs_help":        true,
  "fhir_observation":  { "resourceType": "Observation", "...": "..." }
}
```

Field rules:

- `observation_id` — copy verbatim from the `/predict` response. **Do not regenerate.** This is the cross-reference key for retraining.
- `patient_id`, `device_id`, `timestamp` — copy from the `/predict` response (or the original window).
- `fall_detected` — should always be `true` when you publish, because you only publish on detected falls. The dashboard skips messages where it is `false`, so anything else is wasted bandwidth.
- `confidence`, `model_version` — copy from `inference` in the response.
- `alert_time` — when the popup actually closed (= "now" at the moment of publish).
- `patient_confirmed` / `needs_help` — see section 4.
- `fhir_observation` — full FHIR Observation from the response. Optional in the schema today but useful for downstream consumers; keep it.

`fall_dashboard` ignores any extra fields, so you can include diagnostic data freely.

## 6. Patient Dashboard Side (informational)

You don't have to do anything special for the dashboard side from the mobile app — but for completeness, this is what happens after your MQTT publish:

1. `fall_dashboard` (`mqtt_listener.py`) decodes the payload.
2. Drops it if `fall_detected=False`.
3. Calls `record_fall()` → writes `fall_history` row to Postgres.
4. Calls `broker.publish_local()` → fans out to every connected SSE client.
5. Browsers connected to `GET /api/stream` receive a `data: { ...event... }` event.
6. The Patient Dashboard renders an alert banner.

If you want to test locally without our `fall_dashboard`, just run a `mosquitto_sub -t 'fall/alert/#'` to confirm your payload looks right.

## 7. Local Dev Setup (mirror of production minus BLE)

Until your real mobile app is wired up, you can run the full stack with `mock_app` standing in. From `_6G_Integration_v2_mqtt/`:

```powershell
# Terminal 1 — infrastructure (Postgres, MQTT broker, Prometheus, Grafana, MinIO)
docker-compose -f infrastructure/docker-compose.yml up

# Terminal 2 — inference server
uvicorn inference_server.server:app --host 0.0.0.0 --port 8001

# Terminal 3 — fall dashboard backend
python -m fall_dashboard.main

# Terminal 4 — the stand-in for your mobile app
python -m local_dev.mock_app.main
```

Then open `http://localhost:8002/` in a browser — fall alerts arrive over SSE. To verify the JOIN that retraining depends on, hit `GET /api/falls` and check that each row's `observation_id` also exists in `inference_log` (Postgres).

## 8. The Pieces You Replace, and the Pieces You Don't

| Currently in `mock_app` | What you build | Why |
|-------------------------|----------------|-----|
| `influx_fetcher.py` reads ACC from cloud InfluxDB | Read ACC from BLE wearable | The cloud InfluxDB is a dev-only fake BLE source; in production InfluxDB is FOCUS-hosted and only used for biosignal display. |
| `api_caller.py` POSTs `/predict` | Same — keep behaviour identical | The `/predict` contract does not change. |
| `_simulate_patient_confirmation` always returns `not_answered` after 10s | A real popup with three outcomes (yes / no / timeout) | The mock has no UI. |
| `paho-mqtt` Python client publishes via TCP 1883 | `mqtt.js` over WebSocket 9001 | React Native can't do raw TCP. |

Things you do **not** touch:
- The inference server. Its API is fixed by this document.
- The MQTT broker. We run it; you connect to it.
- `fall_dashboard`. It only listens on MQTT and serves HTTP/SSE — it doesn't care where the MQTT message came from.

## 9. Sample Rate, Window Size, and Why They Matter

The inference server is configured for **9-second windows at 50 Hz = 450 samples**. SmarKo wearables in this trial run at 50 Hz already, so no resampling on the mobile app. If SmarKo ever changes the rate, two things must move together:

1. `HARDWARE_ACC_SAMPLE_RATE` env on the inference server.
2. The number of samples per window in your mobile app's window builder.

If the mobile app sends fewer than 450 samples, the inference server returns a 422. If it sends more, the extras are ignored. If the timestamps don't align (e.g. wearable burst dropped some samples), the server resamples linearly to 50 Hz before feature extraction — no change needed on your side.
