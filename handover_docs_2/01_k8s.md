# Kubernetes Deployment Handover

**Audience:** FOCUS DevOps engineers responsible for installing, upgrading, and operating the fall-detection workload inside the FOCUS K8s cluster.
**Repo / branch:** `_6G_Integration_v2_mqtt/` on branch `6G-integration_with_MQTT`.
**Helm chart location:** `_6G_Integration_v2_mqtt/helm/fall-detection/`.
**Scope of this doc:**
- Cluster prerequisites
- Step-by-step install
- Which images are ours (custom) vs upstream (public)
- Which code/files are shared between images and which are not
- Command list (build → push → install → verify → upgrade → uninstall)

If you only have 5 minutes, jump to section 2 (prerequisites checklist) and section 6 (command list).

## 1. What gets deployed

One Helm chart deploys 8 pods, all into a single namespace inside the FOCUS cluster.

| Pod | Image | What it does | Custom or Public |
|-----|-------|---------------|------------------|
| inference-server | our `inference-server:<tag>` | FastAPI :8001 — receives `/predict`, runs XGBoost, returns fall result + observation_id | **Custom (we build)** |
| fall-dashboard | our `fall-dashboard:<tag>` | FastAPI :8002 — MQTT subscriber, writes fall_history, fans out SSE | **Custom (we build)** |
| mlflow | our `mlflow:<tag>` | MLflow tracking server :5000 (thin wrapper around `mlflow:2.x` + boto3 + psycopg2) | **Custom (we build)** |
| postgres | `postgres:16-alpine` | StatefulSet :5432 — hosts `fall_detection` and `mlflow` databases | Public (Docker Hub) |
| mqtt-broker | `eclipse-mosquitto:2` | Deployment :1883 (TCP) + :9001 (WebSocket) | Public (Docker Hub) |
| minio | `minio/minio:latest` | StatefulSet :9000 — MLflow artifact store, bucket `mlflow-artifacts` | Public (Docker Hub) |
| prometheus | `prom/prometheus:latest` | Scrapes inference-server `/metrics` | Public (Docker Hub) |
| grafana | `grafana/grafana:10.4.0` | 3 pre-provisioned dashboards | Public (Docker Hub) |

Plus two Helm-hook Jobs that run automatically:
- **alembic-migrate** (Helm hook: `post-install,post-upgrade`, weight `-5`) — runs `alembic upgrade head`
- **create-mlflow-bucket** (Helm hook: `post-install`) — `mc mb` against MinIO

### Custom images vs public images — rule of thumb

> If we wrote the Dockerfile, it's custom and goes to **your** registry.
> If the image comes from `docker.io/<vendor>/...`, it's public and pulled directly.

You only need to push 3 images to your registry: `inference-server`, `fall-dashboard`, `mlflow`. The other 5 the cluster pulls from Docker Hub on its own (or from your internal mirror if you have one).

## 3. Step-by-step deploy guide

The full path from "fresh clone" to "running pods on FOCUS cluster":

```
┌────────────────────────────────────────────────────────────────────────┐
│  Step 1   Clone repo + open _6G_Integration_v2_mqtt/                   │
│  Step 2   Edit values.yaml with FOCUS-specific values (Section 2.3)    │
│  Step 3   Build 3 custom Docker images                                 │
│  Step 4   Push the 3 images to FOCUS registry                          │
│  Step 5   Create namespace (or rely on chart's namespace.yaml)         │
│  Step 6   helm install (with --set secrets)                            │
│  Step 7   Verify pods running, jobs succeeded, PVCs bound              │
│  Step 8   (if NetworkPolicy enforced) apply allow-policy               │
│  Step 9   Smoke test /health + /predict from inside cluster            │
│  Step 10  Smoke test public /predict via ingress                       │
└────────────────────────────────────────────────────────────────────────┘
```

Detailed commands are in section 6.

### Sequencing notes

- **Postgres must come up before alembic-migrate.** Helm hook weight `-5` plus the chart's readiness probes handle this — the migrate Job won't start until Postgres replies. If it ever fails, re-run with `helm upgrade --install` and the Job retries.
- **MinIO must come up before create-mlflow-bucket.** Same Helm hook ordering.
- **MLflow depends on Postgres + MinIO.** It boots after both are Ready.
- **inference-server and fall-dashboard depend on Postgres + MQTT + MLflow** for full functionality, but their `/health` endpoints become 200 as soon as their own Python process is up. Real readiness = the migrate Job has finished.

## 4. Which code/files are shared (and which aren't)

This is important when you build the images — the same source folders end up baked into multiple images.

```
_6G_Integration_v2_mqtt/
├── inference_server/      ← in inference-server image only
├── fall_dashboard/        ← in fall-dashboard image only
├── ml_dashboard/          ← admin UI, not yet containerised (run locally)
├── server_health/         ← admin UI, not yet containerised (run locally)
├── ml_pipeline/           ← SHARED → in BOTH inference-server and fall-dashboard
├── shared_db/             ← SHARED → in BOTH inference-server and fall-dashboard
├── config/                ← SHARED → in BOTH
├── model/                 ← in inference-server only (XGBoost .pkl files)
├── retrain/               ← in mlflow image (or run as a Job when needed)
├── helm/
│   ├── fall-detection/    ← THE chart (you ship this to FOCUS)
│   └── mock-focus/        ← LOCAL DEV ONLY — never ships to FOCUS
├── infrastructure/        ← Docker Compose for local dev — does NOT go to K8s
│   └── mlflow/            ← Dockerfile for our custom MLflow image
└── local_dev/             ← LOCAL DEV ONLY — mock_app, mock_focus, dev scripts
```

### Image content matrix

| File / folder | inference-server image | fall-dashboard image | mlflow image |
|---------------|:----------------------:|:--------------------:|:-----------:|
| `inference_server/` | yes | no | no |
| `fall_dashboard/` | no | yes | no |
| `ml_pipeline/` | yes | yes | no |
| `shared_db/` | yes | yes | no |
| `config/` | yes | yes | no |
| `model/` | yes | no | no |
| `retrain/` | no | no | yes |
| `alembic.ini` + `shared_db/migrations/` | no | yes (so the migrate Job can run) | no |
| `local_dev/` | NEVER | NEVER | NEVER |
| `infrastructure/` | NEVER | NEVER | NEVER |

**Rule:** anything under `local_dev/` or `infrastructure/` is local-development scaffolding. Never bake those into a production image. The Dockerfiles in this repo enforce this with explicit `COPY` lists (no `COPY . .` shortcuts).

### Files that are deliberately NOT shared (and why)

- **inference_server has the XGBoost model files baked in** as a startup fallback. fall-dashboard does not need them — it doesn't run inference.
- **fall-dashboard has alembic.ini baked in** — the alembic-migrate Job runs in a fall-dashboard pod (it has the schema files via shared_db). inference-server has no need for the migration runner.
- **mlflow image only contains retrain/** — no application code. It's MLflow plus our boto3/psycopg2 deps plus the retraining CLI.

## 5. Helm chart structure

```
helm/fall-detection/
├── Chart.yaml
├── values.yaml                  ← single file you edit per environment
├── files/
│   ├── postgres-init.sql        ← creates fall_detection + mlflow databases
│   ├── mosquitto.conf           ← MQTT broker config
│   └── prometheus.yml           ← scrape targets
└── templates/
    ├── namespace.yaml
    ├── secrets.yaml             ← pg pwd, minio pwd, api key, grafana pwd
    ├── configmap.yaml           ← shared env (DATABASE_URL, MQTT, MLflow)
    ├── migrate-job.yaml         ← Alembic Job (post-install,post-upgrade)
    ├── inference-server/        (deployment + service)
    ├── fall-dashboard/          (deployment + service + ingress)
    ├── mqtt-broker/             (deployment + service + configmap)
    ├── postgres/                (statefulset + service + configmap)
    ├── minio/                   (statefulset + service + bucket-job)
    ├── mlflow/                  (deployment + service)
    ├── prometheus/              (deployment + service + configmap)
    └── grafana/                 (deployment + service + dashboards configmap)
```

### Chart decisions you should know

- **Postgres is a StatefulSet** with a `volumeClaimTemplates` PVC. One instance hosts two logical databases (`fall_detection`, `mlflow`) — `files/postgres-init.sql` creates both at first boot.
- **MinIO is a StatefulSet** with its own PVC. The bucket `mlflow-artifacts` is created by a one-shot Job on `post-install`.
- **Alembic runs as a Helm hook Job** — you never run migrations manually. Hook weight `-5`, `hook-delete-policy: hook-succeeded`.
- **Ingress uses Traefik.** `spec.ingressClassName: traefik`, no nginx annotations. Traefik handles SSE natively.
- **`replicas: 1` for inference-server.** This is **not defensive** — Prometheus counters and Python timer state are per-process. **Do not scale this up.**
- **MQTT broker exposes both TCP 1883 and WebSocket 9001.** React Native mobile apps need WS; backend services use TCP.

## 6. Command list

Assume the operator's laptop has `kubectl` + `helm` + `docker` configured for the FOCUS cluster + registry. From `_6G_Integration_v2_mqtt/` as cwd.

### 6.1 Build the 5 custom images

The chart ships 5 services we build ourselves: inference-server, fall-dashboard,
ml-dashboard (admin: retrain + hot-swap), server-health (admin: status), and
mlflow (custom image with our pinned version + plugins).

For Docker Desktop local testing, the orchestration script
[`helm/fall-detection/build.ps1`](../_6G_Integration_v2_mqtt/helm/fall-detection/build.ps1)
builds all 4 of the Python services with the `registry.example.com/` prefix.
For a real registry deployment, build manually with the production tag:

```powershell
$REGISTRY = "registry.focus.example.com"   # ← your registry
$TAG      = "v1.0.0"

docker build -f inference_server/Dockerfile         -t $REGISTRY/inference-server:$TAG .
docker build -f fall_dashboard/Dockerfile           -t $REGISTRY/fall-dashboard:$TAG  .
docker build -f ml_dashboard/Dockerfile             -t $REGISTRY/ml-dashboard:$TAG    .
docker build -f server_health/Dockerfile            -t $REGISTRY/server-health:$TAG   .
docker build -f infrastructure/mlflow/Dockerfile    -t $REGISTRY/mlflow:$TAG          infrastructure/mlflow
```

### 6.2 Push to FOCUS registry

```powershell
docker push $REGISTRY/inference-server:$TAG
docker push $REGISTRY/fall-dashboard:$TAG
docker push $REGISTRY/mlflow:$TAG
```

If your registry requires auth, do `docker login $REGISTRY` first. If your cluster also needs an `imagePullSecret`, create it once:

```powershell
kubectl create secret docker-registry focus-registry-creds `
  --docker-server=$REGISTRY `
  --docker-username=<user> `
  --docker-password=<pwd> `
  -n mcs-fall-detection
```

…and set `values.yaml → imagePullSecrets: [name: focus-registry-creds]`.

### 6.3 helm install — primary path

```powershell
# Dry run first (catches values.yaml mistakes early)
helm install fall-detection ./helm/fall-detection `
  --namespace mcs-fall-detection --create-namespace `
  --dry-run --debug

# Real install
helm install fall-detection ./helm/fall-detection `
  --namespace mcs-fall-detection --create-namespace `
  --set registry=$REGISTRY `
  --set images.inferenceServer.tag=$TAG `
  --set images.fallDashboard.tag=$TAG `
  --set images.mlflow.tag=$TAG `
  --set postgres.password=<real-pg-password> `
  --set minio.rootPassword=<real-minio-password> `
  --set grafana.adminPassword=<real-grafana-password> `
  --set inferenceServer.apiKeys=<real-api-key>
```

### 6.4 The override list

If you have a `prod-values.yaml` per environment (recommended), `helm install -f prod-values.yaml ...` instead of `--set` chains. The minimum override list per environment:

```yaml
# prod-values.yaml
namespaces:
  ours:  mcs-fall-detection        # NEW namespace for the fall-detection components we ship this time
  focus: <your-focus-namespace>    # EXISTING FOCUS namespace already running in the cluster (FHIR, InfluxDB, Patient Dashboard)

registry: registry.focus.example.com

images:
  pullPolicy: Always
  inferenceServer: { repository: inference-server, tag: v1.0.0 }
  fallDashboard:   { repository: fall-dashboard,   tag: v1.0.0 }
  mlflow:          { repository: mlflow,           tag: v1.0.0 }

ingress:
  enabled: true
  host:    fall-detection.your-cluster.example.com

postgres:
  storageClass: ""        # or your default

minio:
  storageClass: ""        # or your default

inferenceServer:
  fhirServerUrl: ""       # empty = no FHIR push

imagePullSecrets:
  - name: focus-registry-creds
```

Secrets stay on `--set` at runtime so they never hit git.

### 6.5 Verify

```powershell
# Pods all Running / Completed
kubectl get pods -n mcs-fall-detection

# PVCs Bound
kubectl get pvc  -n mcs-fall-detection

# Migration succeeded
kubectl logs -n mcs-fall-detection job/alembic-migrate

# Bucket creation succeeded
kubectl logs -n mcs-fall-detection job/create-mlflow-bucket

# Inference server reachable in-cluster
kubectl run -n mcs-fall-detection --rm -it --image=curlimages/curl test-curl -- `
  curl http://inference-server:8001/health

# Inference server reachable via ingress (405 expected — POST endpoint)
curl https://fall-detection.your-cluster.example.com/predict
```

### 6.6 Upgrade

```powershell
# Build + push new tag
$NEW_TAG = "v1.1.0"
docker build -f inference_server/Dockerfile -t $REGISTRY/inference-server:$NEW_TAG .
docker push  $REGISTRY/inference-server:$NEW_TAG

# Roll forward
helm upgrade fall-detection ./helm/fall-detection `
  --namespace mcs-fall-detection `
  --reuse-values `
  --set images.inferenceServer.tag=$NEW_TAG
```

Alembic migrations run automatically on every upgrade (Helm hook).

### 6.7 Uninstall

```powershell
helm uninstall fall-detection -n mcs-fall-detection
kubectl delete namespace mcs-fall-detection      # cleans up PVCs too
```

## 7. Ingress notes

The chart ships with `spec.ingressClassName: traefik`. Traefik handles SSE (`/api/stream`) natively — no annotations needed. If you use nginx instead, you must:

1. Change `spec.ingressClassName: nginx` in `templates/fall-dashboard/ingress.yaml`
2. Add the SSE annotations:
   ```yaml
   nginx.ingress.kubernetes.io/proxy-buffering: "off"
   nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
   nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
   ```
3. The path block for `/api/stream` MUST come **before** the parent `/api/` block — nginx matches the first matching location, not the longest prefix.

## 8. NetworkPolicy

If your cluster enforces NetworkPolicy by default, add this on our side to allow the FOCUS Patient Dashboard backend (or browser via FOCUS pod) to call our `fall-dashboard`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-focus-to-fall-dashboard
  namespace: mcs-fall-detection
spec:
  podSelector:
    matchLabels:
      app: fall-dashboard
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: <your-focus-namespace>
      ports:
        - protocol: TCP
          port: 8002
```

We can add this to the chart as `templates/fall-dashboard/networkpolicy.yaml` once you confirm your namespace label.

## 9. Local dry-run (Docker Desktop K8s)

Useful before pushing to FOCUS. Two charts run side by side:

- `helm/fall-detection/` — our real chart (10 services)
- `helm/mock-focus/` — fake FOCUS namespace (mock FHIR + mock InfluxDB + mock Patient Dashboard)

Both charts ship orchestration scripts so the full local dry-run is one
command per phase:

```powershell
# 1. Build images for both charts (parallel could speed this up but ~5 min sequential)
.\helm\fall-detection\build.ps1
.\helm\mock-focus\build.ps1

# 2. Install both charts (each waits for its pods to reach Ready)
.\helm\fall-detection\install.ps1
.\helm\mock-focus\install.ps1

# 3. Open all UI tunnels (each in its own window so they keep running)
.\helm\fall-detection\port-forward.ps1
# → http://127.0.0.1:8002/  fall-dashboard (use 127.0.0.1, NOT localhost — gotcha #16)
# → http://127.0.0.1:8004/  ml-dashboard
# → http://127.0.0.1:8006/  server-health
# → http://127.0.0.1:5000/  MLflow
# → http://127.0.0.1:3000/  Grafana (admin/admin)

# 4. Run automated tests
.\helm\fall-detection\test.ps1            # 8 in-cluster probes for fall-detection
.\helm\mock-focus\test.ps1                # 4 cross-namespace probes
# Browser smoke test: http://localhost:30090/  (mock patient dashboard)

# 5. Tear down both
.\helm\mock-focus\teardown.ps1
.\helm\fall-detection\teardown.ps1
```

Each script verifies `kubectl config current-context` is `docker-desktop` so
you can't accidentally install into a real cluster. See each chart's `README.md`
for what's inside the scripts and how to do the same steps manually.

`mock-focus` validates everything that goes wrong with cross-namespace deployment **before** it reaches your cluster.

## 10. Things that bit us during local testing

These are gotchas we hit on Docker Desktop K8s. Worth checking on your cluster too:

- **`ErrImageNeverPull`** with `pullPolicy: Never` on Docker Desktop is usually the containerd image-store split. Workaround: `docker save | k3s ctr -n=k8s.io image import -` style. On a real cluster with `pullPolicy: Always` + a real registry, this can't happen.
- **MLflow OOM-killed at 1Gi memory limit.** Bumped to 2Gi in `values.yaml`. If FOCUS has tight quota and you halve it back, expect MLflow gunicorn workers to crash silently.
- **DNS-vs-startup-timing:** Postgres is sometimes resolvable but not yet accepting connections when Alembic Job starts. Our `migrate-job.yaml` has a wait-for-pg init container. Don't strip it.
- **Namespace template + `--namespace` flag conflict:** if you have both `templates/namespace.yaml` and `--namespace foo --create-namespace` AND the values point at a different namespace name, you create two namespaces. We pinned `namespaces.ours` in values.yaml — keep it equal to whatever you pass to `--namespace`.
