1. WHAT THIS PROJECT FOLDER IS ABOUT
=======================================================================

This repo implements fall detection for the Charite / FOCUS clinical
monitoring system using SmarKo wearable sensors.

The wearable sends raw accelerometer data. Our inference server (XGBoost
model) decides if a fall occurred. The mobile app shows the patient a
confirmation popup. If confirmed, a MQTT alert is published. The fall
dashboard receives the alert and shows it in the caregiver UI.

Working folder: _6G_Integration_v2_mqtt/


=======================================================================
2. ARCHITECTURE
=======================================================================

a) OUR NAMESPACE (ships to Kubernetes — mcs-fall-detection namespace)
-----------------------------------------------------------------

  inference_server  (:8001)
    - FastAPI app
    - Receives raw accelerometer data from mobile app via HTTP POST /predict
    - Runs XGBoost fall detection
    - Returns fall result + FHIR R4 Observation in the HTTP response
    - Writes inference_log + feature_snapshot to Postgres (background task)
    - Optionally pushes FHIR Observation to FOCUS FHIR server (if configured)
    - NO MQTT client — it never publishes to MQTT

  fall_dashboard  (:8002)
    - FastAPI app
    - Subscribes to MQTT topic fall/alert/# (confirmed alerts from mobile app)
    - On alert: writes fall_history to Postgres, fans out to SSE
    - Exposes REST API for the Patient Dashboard fall panel:
        GET /api/patients — patient list with fall counts
        GET /api/falls    — fall history with confirmation status
        GET /api/stream   — Server-Sent Events live feed

  Supporting services (also in our namespace):
    Postgres    — shared DB for inference_log, fall_history, etc.
    MQTT broker — Eclipse Mosquitto (TCP 1883, WebSocket 9001)
    MLflow      — model experiment tracking
    MinIO       — artifact store for trained .pkl model files
    Prometheus  — metrics scraping
    Grafana     — dashboards (latency, fall rate, model confidence)


b) FOCUS NAMESPACE
------------------

  FHIR Server       — stores patient demographics (name, DOB, ward)
  InfluxDB          — stores biosignals (HR, SpO2 etc.) written by mobile app
  Patient Dashboard — Isa's unified caregiver web app. Has two panels:
                        - Patient info: fetches from FHIR server + InfluxDB (FOCUS side)
                        - Fall panel:   fetches from our fall_dashboard API (:8002)

  FOCUS does not touch our inference server directly.
  The mobile app does — it sends sensor data to our /predict endpoint.


c) OUTSIDE THE COMPUTER (physical hardware)
-------------------------------------------

  SmarKo wearable   — worn by patient, streams raw ACC data via BLE
  Mobile app        — runs on patient's phone, reads from wearable via BLE


d) LOCAL DEV ONLY — never ships to Kubernetes
----------------------------------------------

  local_dev/mock_app/
    Simulates the mobile app. Because we cannot receive BLE data from
    the real wearable during development, mock_app fetches historical
    ACC data from our own cloud InfluxDB (ecosystem-influxdb.smarko-health.de)
    and replays it into /predict. In production, this folder does not exist.

  local_dev/mock_focus/
    Simulates the FOCUS FHIR server locally (FastAPI :8003).
    In production, replaced by the real FOCUS FHIR server URL.

  local_dev/dev_scripts/switch_model.ps1
    Developer tool for hot-swapping the inference model without restart.

3. IMPORTANT CLARIFICATION — INFLUXDB
=======================================================================

There are two separate InfluxDB instances. Do not confuse them.

  OUR CLOUD INFLUXDB (ecosystem-influxdb.smarko-health.de):
    - Used ONLY by local_dev/mock_app as a fake data source during development
    - Has nothing to do with the production system
    - In production, the real mobile app reads from the wearable directly
      and POSTs to /predict — our cloud InfluxDB is not involved at all

  FOCUS-HOSTED INFLUXDB (in FOCUS namespace):
    - Written by the real mobile app (biosignals: HR, SpO2, etc.)
    - Read by the Patient Dashboard backend for the biosignal display panel
    - Our inference server NEVER reads from it
    - Our inference server NEVER writes to it
    - We do not need their InfluxDB credentials
    - They do not need to give us anything InfluxDB-related

Summary: InfluxDB is FOCUS's concern for biosignal display.
         Our inference pipeline has no InfluxDB dependency in production.

4. WHAT ISA NEEDS TO CHANGE IN THE MOBILE APP
=======================================================================

Currently the mobile app only writes raw data to InfluxDB.
The mobile app needs to do TWO additional things:

Step A — Call our inference API after each wearable reading
-----------------------------------------------------------

  Endpoint:   POST http://<inference-server-host>:8001/predict
  Header:     X-API-Key: <key>   (see Section 9 for the key value)
  Body (JSON):

    {
      "patient_id":    "charite-patient-001",      -- patient identifier
      "device_id":     "smarko-wearable-42",        -- optional
      "acc_x":         [-512, -498, ...],            -- raw LSB integers, NOT g
      "acc_y":         [128, 134, ...],              -- raw LSB integers
      "acc_z":         [16300, 16280, ...],          -- raw LSB integers
      "timestamps_ms": [1712345678000, ...]          -- Unix epoch ms, one per sample
    }

  Rules:
    - acc_x, acc_y, acc_z must be RAW LSB integers as recorded by the SmarKo
      hardware. Do NOT convert to g before sending — the server converts internally.
    - At least 450 samples per axis are needed (9 seconds at 50 Hz).
      If hardware runs at 50 Hz, send the last 450 samples.
    - timestamps_ms is required. Must have the same length as acc_x/y/z.
    - pressure and pressure_timestamps_ms fields are optional — the v0 model
      (ACC-only, 16 features) does not use barometer. Only v3 needs it.

  Response (JSON):

    {
      "observation_id": "3f7a1b2c-...",      -- UUID — CARRY THIS INTO MQTT PAYLOAD
      "patient_id":     "charite-patient-001",
      "device_id":      "smarko-wearable-42",
      "timestamp":      "2026-04-27T10:00:00+00:00",
      "inference": {
        "fall_detected": true,
        "confidence":    0.8234,             -- 0.0 to 1.0
        "threshold":     0.5,
        "result":        "High confidence fall",
        "model_version": "v0",
        "window_size":   450
      },
      "fhir_observation": { ... },           -- FHIR R4 Observation (see note below)
      "fhir_pushed":    false                -- true if server auto-pushed to FHIR server
    }

  IMPORTANT: Save the "observation_id" from the response. It must be
  included in the MQTT alert payload in Step B below. It is the key that
  links the fall alert to the original inference record in Postgres,
  which is required for the MLOps retraining pipeline.

  Note on fhir_observation:
    The FHIR R4 Observation is built by the inference server on every call
    and returned in the HTTP response. It encodes the fall result in standard
    FHIR format (SNOMED code 217082002 "Fall event", confidence score, model
    version). It is NOT stored in our Postgres — it is returned for FOCUS to
    use if needed. If FHIR_SERVER_URL is configured, the server also pushes
    it to the FOCUS FHIR server automatically.


Step B — After patient confirmation popup, publish MQTT alert
-------------------------------------------------------------

  After showing the patient the confirmation popup and recording their
  response, publish to MQTT:

  Topic:   fall/alert/<patient_id>
  Broker:  <mqtt-broker-host>:1883

  Payload (JSON):

    {
      "observation_id":    "3f7a1b2c-...",   -- UUID from /predict response (REQUIRED)
      "patient_id":        "charite-patient-001",
      "device_id":         "smarko-wearable-42",
      "timestamp":         "2026-04-27T10:00:00+00:00",
      "alert_time":        "2026-04-27T10:00:15+00:00",
      "fall_detected":     true,
      "confidence":        0.8234,
      "model_version":     "v0",
      "patient_confirmed": "yes",            -- "yes" | "no" | "not_answered"
      "needs_help":        true              -- true | false | null
    }

  patient_confirmed values:
    "yes"          — patient pressed Yes on the fall confirmation popup
    "no"           — patient pressed No (treated as false positive, no caregiver alert)
    "not_answered" — timeout expired, no response (treated conservatively as a fall)

  needs_help:
    true  — patient pressed Yes to "Do you need help?"
    false — patient pressed No
    null  — not answered / timeout (conservative: assume help needed)

  IMPORTANT: observation_id is mandatory. If omitted, the retraining pipeline
  cannot link the patient's confirmation to the model's prediction, and the
  false positive / true positive cannot be used for model improvement.

  Does the SmarKo app already have one, or does Isa add new UI?

6. API REFERENCE — INFERENCE SERVER (:8001)
=======================================================================

POST /predict
  Header:  X-API-Key: <key>
  Body:    (see Section 4, Step A above)
  Returns: PredictResponse (see Section 4, Step A above)

GET /health
  No auth needed.
  Returns: { status, model_version, uses_barometer, sample_rate_hz, uptime_seconds }

GET /model/info
  Returns: { name, uses_barometer, num_features, loaded_as }
  uses_barometer tells whether pressure data is required in /predict.

GET /model/list
  Returns: { available_versions: { "v0": "desc", "v3": "desc", ... } }

POST /model/switch
  Header:  X-API-Key: <key>
  Body:    { "version": "v0_retrained" }
           OR
           { "mlflow_stage": "Production" }
  Hot-swaps the loaded model without restarting the server.

GET /metrics
  Prometheus metrics endpoint. Used by Grafana.

GET /docs
  OpenAPI / Swagger UI — interactive documentation.

7. API REFERENCE — FALL DASHBOARD (:8002)
=======================================================================

GET /api/patients
  Returns:
    {
      "patients": [
        {
          "patient_id":      "charite-patient-001",
          "mac_id":          "6c:1d:eb:04:a9:e6",
          "fall_count":      3,
          "session_started": "2026-04-27T08:00:00",
          "session_active":  true
        }
      ]
    }

GET /api/falls
  Query params:
    patient_id  (optional) — filter to one patient
    only_falls  (default true) — only return rows where fall_detected=true
    limit       (default 200, max 2000)
  Returns:
    {
      "falls": [
        {
          "id":                1,
          "observation_id":    "3f7a1b2c-...",
          "patient_id":        "charite-patient-001",
          "mac_id":            "6c:1d:eb:04:a9:e6",
          "fall_detected":     true,
          "patient_confirmed": "yes",
          "needs_help":        true,
          "detection_time":    "2026-04-27T10:00:00+00:00"
        }
      ]
    }

  Note: alert_time is not currently returned by this endpoint (only
  detection_time is). If needed, add it to db.py list_falls().

GET /api/stream
  Long-lived Server-Sent Events connection.
  Use browser's built-in EventSource API:

    const es = new EventSource("http://<fall-dashboard>:8002/api/stream");
    es.onmessage = (e) => {
      const fall = JSON.parse(e.data);
      // fall has same fields as /api/falls rows + observation_id + fhir_observation
    };

  First event after connection:
    event: connected
    data: {}

  Subsequent events (one per confirmed fall):
    data: { ...same fields as /api/falls + full fhir_observation dict... }

  Keepalive comment every 15 seconds (so proxies don't drop connection):
    : keepalive

  EventSource reconnects automatically on disconnect.
  No auth required on the stream endpoint.

GET /
  Standalone caregiver web UI (for local testing).
  In production, Isa's Patient Dashboard replaces this.

8. MQTT PAYLOAD SCHEMA (complete reference)
=======================================================================

Topic:   fall/alert/<patient_id>
Broker:  <mqtt-broker-host>:1883

Full payload published by mobile app after patient confirmation:

  {
    "observation_id":    string (UUID),   -- from /predict response, REQUIRED
    "patient_id":        string,
    "device_id":         string | null,
    "timestamp":         string (ISO8601),  -- when fall was detected
    "alert_time":        string (ISO8601),  -- when alert was published (after confirmation)
    "fall_detected":     boolean,           -- always true when published
    "confidence":        float (0.0-1.0),   -- model confidence
    "model_version":     string,            -- e.g. "v0"
    "fhir_observation":  object | null,     -- FHIR R4 Observation (optional, can omit)
    "patient_confirmed": string,            -- "yes" | "no" | "not_answered"
    "needs_help":        boolean | null
  }

fall_dashboard subscribes to fall/alert/# (wildcard — all patients).
It only processes messages where fall_detected=true.
If patient_confirmed="no", the message is still stored in Postgres with
label=0 (false positive) — useful for retraining.

LOCAL DEV RUN ORDER (for Isa to test locally)
=======================================================================

From _6G_Integration_v2_mqtt/ as working directory:

  1. docker-compose -f infrastructure/docker-compose.yml up
     (starts Postgres, MQTT broker, Prometheus, Grafana, MinIO)

  2. uvicorn inference_server.server:app --host 0.0.0.0 --port 8001

  3. python -m fall_dashboard.main

  4. python -m local_dev.mock_app.main   (simulates mobile app — local testing only)

  Then open http://localhost:8002/ to see the fall dashboard.
  A fall should appear within ~20 seconds of starting mock_app.

To simulate FOCUS FHIR server locally:
  uvicorn local_dev.mock_focus.fhir_server:app --host 0.0.0.0 --port 8003
  Set FHIR_SERVER_URL=http://localhost:8003 in .env to enable FHIR push.
